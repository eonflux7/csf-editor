    How the flow works

    Read this once and the rest of the page falls into place. The names come from the decoded opcodes and the file's own identifier tables; the csf-info parser is read-only and deliberately does not simulate the VM, so “what runs when” is reconstructed from events, conditions and trigger flags rather than by executing anything.

    One container, two programs

    .gsc and .csc are both CSFFBS documents: an entry table, an identifier table and a string table. The parser turns them into a flat list of typed entries. A GSC is a mission script; a CSC is a cutscene script. Same grammar, different opcode vocabulary.

    Scripts, events, conditions

    Each script has an id, a name, a folder, and flags (trigger, enabled, valid). An ON <EVENT> line registers what wakes it up; optional CONDITION blocks filter the event payload (which zone? which actor?). Then a flat list of actions with a depth that encodes WHILE / IF / FOREACH nesting.

    Events and triggers

    Scripts talk through a named event bus: SEND_EVENT SET_OBJ_01 wakes every script listening for SET_OBJ_01. Ids are a second channel: TRIGGER_EXE 534 runs script 534 immediately, TRIGGER_ON/OFF arms or disarms one, and ADD_SCRIPT bolts a behaviour script onto a freshly spawned actor.

    Zones are SCN polygons

    INIT_ZONAS calls ACT_BICHO_EVENT_ZONA for zones 1–4 and 9–13, which tells the engine to emit BICHO_ENT_ZONA (carrying EVT_ZONA + EVT_BICHO1) whenever an actor crosses the matching area polygon. Cutscenes and tutorials are gated on that event. Zone 32 (SPAWN) is used the other way round — the spawner checks the player is not in it.

    Objectives and text

    HUD objectives are driven by SET_OBJETIVO, SET_OBJETIVO_LABEL, SET_OBJETIVO_DUMMY_V2, SET_MINIMAPA_DUMMY, SET_OBJETIVO_SUCCESS and SET_MISSION_SUCCESS. The FLI operand is a text key resolved in GlobalEK/Texts/Ransom.fli — the page shows those strings inline.

    The GSC ⇄ CSC handshake

    A GSC CUT_* script owns the gameplay: fades, third-person camera, actor placement, subtitles, sounds. It calls CUTSCENE_EXE <id>. The CSC script with that id starts a camera lane (a *_GENERAL_Cámara script full of CAMARA_EN_DUMMY + PAUSE), and a sibling *END script WAIT_CONDICIONs on CUTSCENE_FINISHED. When the lane ends, the GSC fades back and gameplay resumes.

    What the parser can and cannot tell you

    • Exact: every script/event/condition/action/operand, its entry index and byte offset, zone membership, actor and dummy placement, and all FLI text.
    • Not simulated: runtime timing of cutscene actions is ordered/unknown unless a PAUSE states a duration, and gameplay semantics of an opcode are inferred from its name and operands. Scripts flagged enabled=false are dead in this build.
    • Many-to-many: the BICHO ids in a script are SCN actor ids; the map uses the Objetos.bdd class names where the tool resolved them.
