# RWS Lightmaps Blender add-on

This add-on configures a glTF scene exported by CSF RWS Tools for material and
lightmap inspection in Blender 4.0 or newer.

## Install

1. In Blender, open **Edit > Preferences > Add-ons**.
2. Choose **Install from Disk** and select `rws_lightmaps.zip`.
3. Enable **Material: RWS Lightmaps** if Blender does not enable it automatically.

## Use

1. Import the `.gltf` generated by CSF RWS Tools into a clean Blender scene.
2. In the 3D View, press `N` and open the **RWS Lightmaps** tab.
3. Click the folder beside **Manifest** and select the sibling
   `.manifest.json`. The sibling `Textures` directory is filled automatically.
4. Confirm the discovered **Textures** path, changing it only if the resources
   live somewhere else.
5. Press **Configure Imported Materials**.
6. Use **Base**, **Lightmap**, or **Base x Lightmap** under Viewport Mode.
7. Use Material Preview or Rendered viewport shading.

The panel keeps the normal configure, bake, and export workflow compact. Enable
**Show Advanced Options** for color handling, the preview Sun, Cycles tuning,
lighting diagnostics, and DDS encoder settings.

The add-on uses the first mesh UV layer for base textures and the second for
lightmaps. Its generated emission shaders make the selected texture mode visible
without additional Blender lights. **Reload RWS Images** refreshes images edited
or rebaked outside Blender.

**Legacy Base DDS Color** is enabled by default because CSF's fixed-function
renderer uses the stored gamma-encoded DDS values directly. Blender's normal sRGB
decode makes these assets look substantially darker. Lightmap and combined modes
default to CSF's `2.0x` lightmap modulation; **Lightmap Intensity** can override it.

The base texture's alpha channel remains the opacity mask in all three viewport
modes, so foliage cards do not show the black RGB stored below transparent DDS
texels. `FFLR*` floor textures are kept opaque because their DXT3 alpha data is not
surface opacity in CSF.

The material configuration is intentionally non-destructive to geometry and UV
data, but it replaces each matched material's active surface connection with the
generated RWS preview shader. Work in a copy of the `.blend` file if existing
custom material graphs matter.

## Cycles bake setup

The panel can prepare selected meshes for a diffuse light-only Cycles bake:

1. Save the `.blend` and start with a small test area.
   Choose **Bake Resolution** before preparing: `1x` retains the source DDS
   dimensions, `2x` doubles width and height, and `4x` quadruples both. Thus,
   `2x` costs roughly 4 times as many pixels and `4x` costs roughly 16 times as
   many. FR01's complete set of floating-point targets is about 223 MiB at `1x`,
   892 MiB at `2x`, and 3.5 GiB at `4x`, before Cycles and scene memory.
2. Use **Select World Sectors** for static map geometry, or select meshes manually.
   Some maps also contain clump terrain shells whose vertices duplicate the
   RenderWare world floor with only a tiny height offset. These shells obscure
   the prepared floor and cause viewport shimmer. The selector detects clumps
   made entirely from `FFLR*` floor materials, verifies their vertices coincide
   with world vertices, and hides only those confirmed duplicates from viewport
   and render. The objects remain in the `.blend` and can be unhidden manually.
3. Press **Prepare Selected for Bake**. The add-on creates one correctly sized,
   Non-Color `RWS_BAKE_*` image per referenced lightmap, shares it across matching
   materials, makes it the active bake target, and temporarily substitutes a
   base-textured diffuse shader so scene lighting remains easy to arrange. The
   actual Diffuse bake disables its Color contribution and therefore still writes
   illumination only. Targets use floating-point pixels so highlights are retained;
   existing foliage opacity masks remain connected. It also enables scene lights
   and scene world in 3D viewports and switches the invoking viewport to Rendered
   shading, so the lighting being prepared for the bake is visible.
4. Add and arrange your own lights, or press **Add Strong Preview Sun** for a
   known-visible starting light. A Sun's position has no effect; rotate it to
   change the light direction. Adding a light deselects meshes in Blender, but
   the add-on remembers the objects marked during Prepare.
5. Set **Bake Margin** (4 pixels is a safe starting point) and press **Bake Selected
   Lighting**. The remembered prepared objects are reselected automatically, and
   direct and indirect lighting are baked without base color in one native Cycles
   job. The add-on does not poll, redraw the UI, or split the work into per-atlas
   jobs, avoiding progress-reporting overhead during large bakes.
   On an RTX card, press **Apply RTX Fast Bake Preset** first. It selects OptiX
   (falling back to CUDA), enables GPU rendering, uses 32 adaptive samples, and
   removes glossy, transmission, and volume bounces that do not contribute to
   these diffuse lightmaps.
6. Save all generated `RWS_BAKE_*` images before closing Blender, then press
   **Restore Preview Shaders** to return to the Base/Lightmap preview.

Repeated placed meshes can share the same original UV atlas, so baking multiple
placements at once may write overlapping pixels. Begin with World Sectors or one
object group and inspect the result. During Prepare, selected materials receive
bake targets while every other visible RWS material is temporarily changed from
its self-lit preview shader to a base-textured passive diffuse surface. Trees and
other clumps therefore cast shadows and reflect ordinary illumination without
acting as area lights or receiving overlapping lightmap writes. **Restore Preview
Shaders** reconnects the preview Emission shaders for both groups.

**Bake Selected Lighting** launches Cycles as Blender's native background bake
job, keeping the window responsive while the bake runs. The panel reports elapsed
time, Blender's status bar continues to show native bake progress, and `Esc`
requests cancellation. Completed targets are marked exportable only after Blender
reports that the entire bake job completed successfully.

## Game-ready DDS export

After a successful bake:

1. Set **Bake Export Root** to a separate staging directory. Never select the
   unpacked source directory itself.
2. Leave **CSF RGB Scale** at `0.5` unless intentionally changing the game's 2x
   lightmap modulation balance.
3. Choose **DDS Format**:
   - **Original BC1/BC2** preserves each source lightmap's compressed format.
   - **32-bit Raw (A8R8G8B8)** writes lossless 8-bit RGB in a legacy DDS with
     opaque alpha. This is the highest-quality option, but consumes four bytes
     per texel (about 85.3 MiB for a 4096-square texture with mipmaps).
4. Enable **Overwrite Existing Exports** only when replacing an earlier staged run.
5. Press **Export Game-Ready DDS**.

Export accepts only targets completed by a verified add-on bake. It also rejects
unverified targets. Targets that appear uniformly gray or black produce a warning
but are still exported because valid sparse UV islands can evade lightweight
sampling.

DDS encoding runs incrementally so Blender remains responsive. Both built-in
writers stream bounded image-row chunks and build mipmaps in temporary disk-backed
buffers, avoiding full-atlas float and mip copies in memory. NVIDIA input TGA
staging is streamed the same way. The panel shows the current file, encoding
phase, exact percentage, and elapsed time. Press
**Cancel DDS Export** or `Esc` to stop after the current small block row. The
unfinished `.tmp` file is removed, while already completed staged DDS files remain
valid and can be overwritten on the next run. A separate counter shows completed
DDS files versus the total planned files and increments after each atomic rename.

For much faster 2x/4x export, install NVIDIA Texture Tools Exporter and select
**DDS Encoder: Auto** or **NVIDIA NVTT**. The add-on detects `nvcompress.exe` or
`nvtt_export.exe` on `PATH` and in NVIDIA's standard installation directory; an
explicit executable can also be selected. It creates a temporary lossless 32-bit
TGA using vectorized pixel conversion, invokes native BC1/BC2 compression at the
appropriate CUDA-capable setting, validates the output dimensions, legacy FourCC,
and mip count,
then atomically installs the DDS. Auto falls back to the portable Python encoder
when NVIDIA's tool is unavailable. NVIDIA mode instead reports a clear error.
For `nvcompress` 3.2.x, the add-on uses that tool's required single-dash mip
options; BC2 uses Normal rather than Fast because 3.2.4 reports that Fast BC2
falls back to its CPU compressor. NVTT 3.2.4 also stops block-compressed mip chains
at 2x2 even when a 1x1 minimum is requested; the add-on appends the tiny terminal
1x1 BC block itself so the output retains CSF's complete source mip chain.

Bake targets are resized and reused when source dimensions change, rather than
leaving large suffixed images in memory. The add-on finds every completed
`RWS_BAKE_*` target, preserves the corresponding
original DDS DXT1/DXT3 format and alpha source, writes the selected 1x/2x/4x
dimensions into the DDS header, extends the mip count for enlarged images, encodes
a complete mip chain, and recreates the archive hierarchy below the chosen root.
For example, an FR01 export root receives:

```text
<export root>/Ransom/Maps/FR01/Textures/SUELO_Lm.dds
```

It also writes `<export root>/rws_bake_export.json` as a receipt containing every
output path and format. The raw writer emits the same legacy `A8R8G8B8` masks
accepted by rws-man and includes the complete scaled mip chain. It does not
require NVIDIA Texture Tools; the encoder setting applies only to Original
BC1/BC2. The built-in legacy BC1/BC2 encoder also requires no external tools.
Copy the produced archive directory into the corresponding unpack before running
the existing archive packer.
